# 实施发现

- `标题Prompt.txt` 是当前优先级最高的标题规则：Item Name ≤75，Item Highlight ≤125，二者职责不同。
- 两份历史笔记仍包含旧式“完整标题 ≤200、建议 150–170”规则，与当前 75+125 契约冲突，不能将原文无差别拼接给模型。
- 历史笔记的标题三段式经验仍有价值：第一段适合映射到 Item Name；第二段和第三段的补充属性、替代词、场景适合映射到 Item Highlight。
- 五点有效知识来自两份笔记：设计/穿戴、鞋头、鞋跟/防滑、搭配/场景、注意事项/尺码/材质，且只能使用标题和产品资料中有证据的特征。
- 长描述原文规则较少：有模板、最后放注意事项。需要基于该意图整理为产品身份、结构/体验、场景/搭配、事实注意事项的稳定框架，但不能虚构来源中没有的营销承诺。
- 应排除广告、选品、供应链、退货、物流、定价、图片/视频编排等与 Listing 文案生成无关的段落，避免稀释提示词。
- 最佳部署结构：用 Vite `?raw` 在构建时打包三份 UTF-8 原文，应用运行时无需访问本地绝对路径；请求发送经过冲突消解的精炼知识，查看弹窗同时提供“实际注入内容”和三份原文。
- 用户最终选择更直观的三提示词结构：标题框直接等于 `标题Prompt.txt`；五点框提炼“设计/穿戴、鞋头、鞋跟/防滑、搭配/场景、注意事项”；长描述框提炼“模板结构 + 最后注意事项”。不再把提炼知识与原文节选混成一个超长系统提示词。
- `SKU标题.docx` 示例有两种五点排版，稳定共同点是方括号小标题；用户明确要求再加序号，因此目标格式为 `1. [Heel & Height] 正文`，中文同构。
- `SKU标题.docx` 长描述以独立大标题开头，随后多个自然段，可带 `Key Features`/适用场景/规格列表，最后用一句与产品和场景相关的优雅文案收束。
- 首页上传使用 document 级 dragenter/dragover/dragleave/drop 和计数器防止闪烁；Listing 页更适合把同样交互限定在产品参考图上传区，避免拖图时影响其他页面区域。
- `generateListingCopy` 已有 `onTextDelta` 底层支持，但 Listing 页面没有传回调或保存原始返回；可复用 `PlannerRunDetailsModal` 展示状态、尝试、模型和实时响应。
- 真实生成结果暴露了核心问题：旧规则把“资料不足时不要编造”与“第五点写注意事项/长描述补缺失注意事项”放得太近，模型便把 `fastening and wear method details were not provided` 等内部审计句直接写进买家文案。
- 用户给出的目标范文不是参数汇总，而是“已确认特征 → 消费者利益 → 穿着画面”的销售表达；五点格式为 `序号 + [利益导向小标题] + 冒号 + 1–2 句正文`，长描述使用 Markdown 强调、适用场景列表、规格列表和情绪化但不新增事实的结尾。
- 标题生成需要减少重复系统指导：标题提示词已经包含 75/125 等业务知识，请求层只额外保留禁用逗号和独立单词 `and`；长度由结构化输出 Schema 与本地验证负责。
- 当前 `LISTING_COPY_SCHEMA` 对所有双语字段共用一个无长度限制 Schema，75/125 只存在于提示词和本地校验；可为两个标题字段建立专用 Schema，用 `maxLength` 兜底而无需在系统散文中重复说明。
- 当前固定契约反复强调 `never infer`、`unsupported facts`，却只说把缺失内容放进 `missingFacts`，没有明确禁止把“not provided/未说明”写进公开字段；需要建立公开文案禁用审计措辞的本地校验，触发既有的一次自动修复。
- 当前安全 HTML 转换只支持标题、段落和列表，不解析用户目标范文中的 `**强调**`；应先 HTML 转义，再确定性地将单行 `**...**` 转为 `<strong>`，并识别加粗的段落标题，继续禁止模型原生 HTML。
- 旧草稿会持久化上一版三个默认提示词；只改常量无法改善已有用户。需要识别上一版默认值并迁移到新版，同时保留真正的自定义提示词。
- 2026-08-14 本地页面检查：当前五点与长描述提示词在视觉上被大量“不得、禁止、缺失、未提供、不能”等负向约束占据，创意目标只占少量段落；即使规则意图正确，也会让模型优先采取低风险、机械复述的策略。
- 本地浏览器为新的独立会话，页面显示默认提示词且 AI 策划配置缺少 API Key，无法读取用户另一浏览器中的已编辑提示词或复现付费生成；但页面结构和当前默认请求约束已经足以确认输出契约没有承载 ChatGPT Web 那种商品身份推理与关键词取舍说明。
- 当前结果区只预留 Item Name、Item Highlight、五点和长描述字段，没有用于展示“图片识别节点 → COSMO 商品身份 → 关键词分层 → 标题取舍 → 可选待确认属性”的策划说明字段；同一模型在被要求直接填严格 JSON 短字段时，会自然省略 Web 对话里的分析过程。
- `ApiProfile` 当前没有推理强度字段，因此 Listing 请求不存在“配置了高推理但漏传”的直接 bug；同模型效果差异更主要来自任务形态：Web 允许长篇分析，而工作台要求一次性严格 JSON 并可能自动二次改写。
- 确认关键退化路径：`performRequest` 把存在 `previousRaw` 的修复请求强制设为纯文本，`generateListingCopy` 又显式传入空参考图。任何长描述加粗/场景/规格格式问题都会触发整份 JSON 重写，第二次模型看不到图片，容易把图片中的花卉、透明感、防水台、穆勒结构等核心识别节点丢掉。
- `validateListingCopyResult` 当前把审美结构偏好当成硬错误；应缩小自动修复范围到 JSON、标题边界、字段缺失、五点数量/基本前缀和公开缺失措辞。加粗、固定章节和优雅收尾应由提示词引导或作为 UI 提醒，不能触发无图重写。
- `ListingCopyResult` 可向后兼容地新增可选/默认空字符串的 `titleAnalysis`，解析旧历史时自动补空；新严格 Schema 则要求同一次看图生成完整策划说明。
- 自动修复不再因为长描述缺少某个固定章节而启动；真正需要修复时优先复用首轮参考图，只有接口明确拒绝多模态输入才降级到纯文本，避免视觉身份信息在第二轮消失。
- 五点与长描述的事实边界应区分“客观断言”和“营销诠释”：材质、尺寸、结构、性能、认证必须有依据；对清晰轮廓、花卉、光泽、色彩带来的审美感受、穿搭灵感和合理场景可以积极发挥。
- 标题策划说明采用安全 Markdown 渲染，可表达商品身份链、COSMO 关系、主副标题关键词分配与待确认高价值属性；主标题和辅助标题仍保留为单独可编辑、可复制字段。
- 当前浏览器连接无法访问用户原有 Chrome 会话，且上一轮本地标签已被清理；不能读取用户浏览器存储。可通过新开本地页面核对代码当前默认值，但“当前提示词”若指用户手工编辑版，只能以页面可见文本为准且不应覆盖真正自定义内容。
- 新开的当前本地页面显示：五点提示词以“懂时尚审美、消费者心理与 Amazon 转化”开头，长描述提示词以“时尚与生活方式品牌的高级创意文案”开头；它们与 `DEFAULT_LISTING_BULLETS_PROMPT` / `DEFAULT_LISTING_LONG_DESCRIPTION_PROMPT` 完全一致，已是页面恢复按钮和新草稿使用的默认值。
- 当前合规规则只笼统写“性能必须有依据”，没有区分普通营销描述和需测试/认证的客观承诺，容易让模型把 `anti-slip`、`strong grip`、`all-day comfort`、`stable and easy to walk` 一律当成不可用性能宣称，并在 `complianceWarnings` 里制造无价值警告。
- 最合适的方案不是在“修正合规规则”和“继续对话”之间二选一：合规规则负责首次生成不误判；继续优化入口负责用户对某一款商品的具体补充。定向优化会带上当前完整 JSON、原始资料和参考图，并要求保留用户未点名的优质字段。
